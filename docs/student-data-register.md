# Student journey data register
Planning baseline: 16 October 2026. Proposed requirements, not an approved integration catalogue.
“Data” is interpreted from the requested “days”; no delivery-day estimates are implied.

## Evidence labels
- **Verified public information**: an official page/service exists; this does not establish an API, caching licence or private access.
- **Verified platform capability**: vendor supports the function; Glasgow enablement and approval remain unknown.
- **Candidate**: a likely system/owner based on current evidence or organisational context; validate before designing against it.
- **Approved integration**: requires an owner-confirmed interface, permissions, support, retention and data contract. None of the private integrations below has been verified as approved for this prototype.

## Minimum source contract before implementation
For every D-record, capture: accountable service owner and technical contact; authoritative fields; API/feed/export documentation and version; licensing/permission; environment and synthetic test accounts; identity/ID mapping; request/response examples; student-level authorisation; scope and cohort exceptions; timestamps/timezone; pagination; stable IDs/revisions; cancellation/deletion; rate/size/time limits; error/stale/empty semantics; owner-agreed freshness; data minimisation/classification; retention/deletion; support/change notification; reconciliation and outage fallback.

Public HTML access does not establish an authorised API. Do not invent endpoint URLs, scrape authenticated screens, use a shared administrator token, or put credentials into EXPO_PUBLIC variables.

## Proposed data-access requests, in order
1. **Identity + MSDI + Timetabling:** synthetic student identities, programme/enrolment data and reuse of the existing CMIS/MyCampus mobile integration. Validate programme exceptions before selecting a pilot.
2. **Learning-platform owner + Registry + Schools:** read-only courses, assessment deadlines and released-results authority; assess Moodle/plugin API and official-app restriction. Agree individual-deadline and release semantics.
3. **EC/Wellbeing + Disability:** correct current policy routes and portal handoffs now; minimal status/outcome integration later, with specialist review.
4. **Estates + Library + Web Team + student organisations:** validated locations/accessibility and approved event/booking feeds, coverage and reuse rights.
5. **Finance + Accommodation + Careers + enquiry-service owners:** source inventory, secure handoffs and minimum useful private reads.

These are proposed requests, not messages sent or permissions granted. Role owners are hypotheses until confirmed; no named colleague has committed work.
